# CloudNova Track B — pre-implementation specification

Status: **proposed before implementation; assumptions require validation against the supplied data and brief.** This file is a handoff artifact, not evidence that an implementation or evaluation has already happened.

## Outcome and boundaries

Build a reproducible local invoice-cleaning pipeline and a narrow natural-language-to-query interface for the six questions in `../source/business-context.md`. Each supported answer must show the SQL and the parameters used. The interface must reject unsupported questions explicitly rather than fabricate a result. A documented, deterministic question-template parser is acceptable for this bounded scope; disclose that it is not general-purpose natural-language understanding. If time permits, an optional language-model translator may be added only behind the same query safety controls, with the offline path remaining runnable. Do not invent credentials or results.

The source file contains 5,125 rows, 5,000 distinct invoice IDs, 82 exact duplicate rows, and 43 invoice IDs with non-identical records, as observed in the staged file. These observations are descriptive, not expected business totals. Preserve the raw file untouched. SHA-256: `f542bc1f8193ab367e0a009a7afe56620335ce23b5817f5edc0ed4f896c89d84`.

## Sources of truth and explicit assumptions

1. The employer's `../source/assessment.md` and `../source/business-context.md` govern the work. Preserve their original text and distinguish brief requirements from choices below.
2. **Record grain:** one canonical record per `invoice_id`. Remove parsed-field-identical duplicates. For conflicting records with the same invoice ID, no authoritative update timestamp is supplied: retain the first row in original file order as a deterministic, provisional rule; record all competing rows and conflict counts in a quality report. Do not claim the retained row is the latest or correct. Explain that selecting a different winner can change results.
3. **Date parsing:** support ISO `YYYY-MM-DD`, `YYYY/MM/DD`, month-name dates, slash-separated month/day/year, and hyphen-separated day-month-year. If the day and month are both plausible, apply that format convention and record an ambiguity flag. Quarantine invalid/unparseable dates from date-dependent calculations; report counts. This is an assumption, not information provided by the customer.
4. **Status and categories:** case/whitespace-normalize and explicitly map the brief's variants, including `completed`/`complete`/`success` → `paid`, `awaiting`/`in_review` → `pending`, `error`/`declined` → `failed`, `charged_back`/`refund` → `refunded`, and `cancelled`/`canceled` → `void`. Normalize `Start`/`Tier 1` → Starter, `Professional`/`Tier 2` → Pro, and `ENT`/`Tier 3` → Enterprise; billing-cycle variants → monthly/annual. Unknown values must be reported and excluded from dependent calculations rather than guessed.
5. **Amounts and FX:** parse currency symbols and grouping separators into `Decimal`/fixed-precision cents; apply USD=1, EUR=1.08, GBP=1.27. Report invalid amounts/currencies; do not silently replace them with zero. When amount text and currency column disagree, flag the row and exclude it from currency-dependent metrics pending a documented decision. Preserve negative refund signs; flag positive refunded values instead of silently flipping them.
6. **Revenue:** recognized/net revenue is the sum of normalized USD amounts for `paid` plus negative amounts for `refunded`; pending, failed, and void are excluded. For “paid invoices in 2024,” show the paid-only figure and, separately, the negative refund adjustment and net figure if the question is ambiguous. Filter by normalized invoice date and disclose exclusions.
7. **MRR:** list prices are USD per seat per month: Starter 49, Pro 99, Enterprise 299. Account MRR = monthly list price × seats × (1 − discount_pct/100); annual billing changes the invoice amount (10 months billed) but not underlying MRR. Do not divide an annual invoice by 12, apply FX again to USD list prices, or sum a customer's MRR once per invoice.
8. **Account snapshot:** where a question asks current account-level MRR, churn, region, plan, or CSAT, select one latest valid invoice by parsed invoice date per account after invoice dedup; deterministic ties use the first source row. The `churned` field is a present/since-churn flag, not a dated churn event. Treat latest `churned=false` as active for current MRR; report invalid or missing flags and missing dates. Do not claim a historical churn rate or a contract renewal/cancellation date. Current average MRR per account is the average across active accounts in that region, one snapshot per account. Churn by plan = distinct churned accounts / distinct accounts with known churn status in that latest-snapshot plan. Clearly label this as a snapshot assumption.
9. **Other questions:** total refunds as a signed negative USD adjustment (optionally show its positive magnitude separately); top five accounts rank by net recognized revenue across all dates, with deterministic tie-breaking and CSAT from the latest account snapshot described above; pending/failed exposure is the sum of their positive normalized amounts and count of canonical invoices, with invalid or negative anomalies disclosed. The dataset's `csat_score` is nullable: do not interpret missing as low or high.
10. Validate IDs, numeric seat/discount ranges, boolean forms, missingness, and other dirty fields. Keep noncritical nulls as null; flag malformed emails and unknown categories. Report input counts, exact duplicates, conflicting IDs, invalid/excluded records, and assumptions. Avoid logging contact emails or exposing them in summary output.

## Minimal implementation contract

- Use a small, inspectable, repeatable local pipeline. Python standard library and SQLite are a sensible default for the one-hour budget; other choices need a reason. Keep raw, cleaned, rejects/conflict report, and query layers distinct. SQLite access should be read-only for queries, use parameter binding, restrict supported statements/templates, and never execute arbitrary model-generated SQL without validation. Avoid network/API dependencies for the required demo.
- A single documented command after setup builds the data and launches or executes the demo, for example `python -m app --question "..."`; the actual chosen command must run from a clean checkout. Return the question, generated SQL plus parameters, and result, and communicate exclusions and snapshot assumptions.
- Support each of the six customer questions in the briefing, including appropriate question variants; where a rule cannot be satisfied, report the limitation instead of presenting an incorrect answer. If scope is reduced under time pressure, clearly mark unmet requirements and prioritize a truthful working core.
- Do not embed secrets, use untrusted data as instructions, expose a broad SQL interpreter, send the ledger externally without user authorization, or silently make unsupported claims. The brief allows a local vector store or framework but Track B does not require either.

## Evaluation contract

Use independent, hand-calculated fixtures with explicit expected values, including: duplicate invoice conflict; mixed/ambiguous dates; exact FX and negative refund treatment; annual billing's 10-month charge vs unchanged MRR; distinct-account MRR and churn despite multiple invoices; missing CSAT/invalid fields; and unsupported-question rejection. Example fixture: a paid EUR 100 invoice is USD 108.00, a EUR -20 refund is USD -21.60, net USD 86.40; a two-seat Pro account at 10% discount has MRR USD 178.20 and a 10-month annual charge USD 1,782.00 before currency conversion. Explicitly keep one **expected failure** (e.g., a historical churn-date query that the data cannot support) and make the harness report it as an expected failure, not hide it or claim a pass. Check that at least five meaningful cases run, the six brief questions are covered or gaps marked, and source-derived overall values are not presented as independently verified unless independently calculated.
